# Backup and restore

Invoices are legal records: back up the database **and** the documents, and rehearse restores.

## What is backed up

| Data | Where | Tool |
| --- | --- | --- |
| Database (all records, issued representations, audit, compliance records) | `postgres` service | `pg_dump --format=custom` |
| Documents (PDFs) | `documents` volume | `tar` |

PDFs can be regenerated byte-for-byte from the issued representations, but backing them up avoids relying on that.

## Docker Compose

From `deploy/`, with the stack running:

```bash
bash scripts/backup.sh ./backups
```

This writes `raccord-db-<stamp>.dump`, `raccord-documents-<stamp>.tgz` and a `.sha256` file. The files are assembled in a hidden temporary directory and published only after both exports and the checksum manifest succeed, so a failed export does not leave a backup set that looks complete. Copy successful sets off the host (encrypted) and schedule the script (for example nightly via cron). `deploy/backups*/` is git-ignored.

Set `RACCORD_BACKUP_RETENTION_DAYS` to control local retention; it defaults to 30 days. The cleanup runs only after the new manifest is published. The manifest timestamp is the recovery point used by `restore.sh`.

### Restore

```bash
bash scripts/restore.sh ./backups <stamp>
```

The script verifies checksums, stops `web`, recreates the database schema from the dump (which also restores the append-only triggers), restores the documents, and starts `web`.

### Rehearsal (performed 2026-10-14)

1. Started an isolated seeded stack as `COMPOSE_PROJECT_NAME=raccorddrill` and verified `/health/ready`.
2. Ran `scripts/backup.sh`; the database dump, document archive and SHA-256 manifest were created.
3. Started a second empty stack as `COMPOSE_PROJECT_NAME=raccordrestore` on another port and ran `scripts/restore.sh`; both checksums verified.
4. Verified the restored stack was healthy, contained the same 26 application tables and preserved the same seeded row counts: 2 customers, 2 projects, 7 billable lines, 1 user, 2 invoice series and 1 issuer profile.

The drill also found and fixed a deployment defect: published runtime files were owned by `root` with mode `660`, which prevented the non-root migration process from reading `Raccord.Web.runtimeconfig.json`. The image now assigns `/app` to the runtime user.

Repeat this rehearsal after every major upgrade.

## Azure

- PostgreSQL Flexible Server keeps automated backups for 14 days (point-in-time restore); raise retention for production.
- Blob soft delete (30 days) and versioning are enabled for documents.
- For long-term retention, export with `pg_dump` and copy the container with AzCopy to a separate, immutable storage account.

## Retention

Spanish rules require keeping invoices and records for years; confirm the period with your advisor (open question in `CHG-INITIAL`) and size retention accordingly.
