## Context

See `proposal.md` for motivation and `specs/cross-surface-design-system/spec.md` for the behavior contract. The frontend already owns CSS variables matching `docs/design/color-tokens.md`; `src/public-site/styles.css`, `tools/static-site/static-site.mjs`, and `tools/arc42-snapshot/render.mjs` carry separate values. The public root HTML generated by `src/public-site/build.mjs` currently contains one unstyled link and relies on `locale.mjs` to redirect.

The product graph has no design-system or brand workflow. The only product requirements this design depends on are WCAG 2.2 AA, the Spanish and English interface, and responsive web usability. The mobile requirement's direct and indirect neighbors (warehouse and working-day behavior) were checked and excluded because no mobile workflow behavior changes.

## Goals / Non-Goals

**Goals:**

- Retain the values already used by the app as the starting canonical palette, then complete and document the missing shared roles with contrast evidence.
- Make consumers reference a single CSS source without introducing a production dependency.
- Give static build outputs the same tokens as the interactive app while allowing surface-specific layout and content.

**Non-Goals:**

- Replacing any surface's information architecture or adding product workflows.
- Changing API, data, deployment, or public product claims.
- Requiring identical page composition or forcing diagrams and operational reports into marketing-page layouts.

## Decisions

- **Keep the existing app token values as the shared palette baseline.** They already match `docs/design/color-tokens.md` and keep the authenticated app stable. The competing public lime/forest palette and engineering report blue/neutral values are rejected as separate brand systems. Extend the palette only for missing roles and verify contrast before adoption. The owner reviews this proposed direction at the Planned gate.
- **Create a shared CSS token source under `docs/design/`.** The frontend imports it; the public build copies it into its output; engineering report and architecture snapshot generators embed or consume it during static generation. This keeps the source available to the Cloudflare Pages build rooted at `src/public-site/` and to the GitHub Pages engineering build, without a package or runtime dependency.
- **Map each surface's local variables to canonical tokens.** Keep local aliases for page-specific layout and chart roles, but make their shared colors, typography, spacing, focus, surfaces, shape, and semantic statuses reference canonical tokens. Preserve light/dark preferences where they exist by mapping both themes to documented semantic tokens.
- **Guard both the source and consumers.** Add a dependency-free Node check that parses the canonical token definitions and verifies that the app stylesheet imports them, the public build emits them, and engineering generators consume them. Fail with the surface/token when a shared value is redefined outside the canonical file.
- **Keep generated snapshots self-contained.** Static HTML must remain usable after publication without network requests for styles or fonts; embed the shared CSS tokens at build time and preserve current content and accessibility affordances.
- **Make the public root useful without script execution.** Generate a styled static locale choice with links to both language roots, retaining browser-language redirection as a progressive enhancement. This fixes the current single-link fallback without making locale selection a new workflow.
- **Do not change architecture boundaries.** No new production package or application layer is needed; this follows the existing CSS and static-site build seams described by `docs/architecture/architecture-rules.md`.

Product requirements retained as constraints are accessibility, localization, and responsive web usability. Accessibility's billing and invoicing journey neighbors, localization's billing and invoicing journey neighbors, and mobile usability's working-day and warehouse neighbors (including their related use cases and rules) were checked; none are changed by this presentation-only proposal.

## Risks / Trade-offs

- [The app palette may not be the final visual direction] → Treat this as the proposed owner-reviewed baseline; resolve approval at the Planned gate before implementation.
- [Static generators could drop required styles or accessibility behavior] → Add output assertions and capture representative generated pages at desktop and narrow widths.
- [Token rules could block intentional chart-specific colors] → Scope the checker to shared tokens and permit documented semantic data-visualization roles.
- [A local CSS source path could break when the public Pages build runs from its configured root] → Exercise the production build command from `src/public-site/` in CI and assert the generated root and locale pages include the tokens.

## Migration Plan

1. Add and verify the canonical token file and design guidance.
2. Adopt the tokens across the app and the public and engineering build outputs.
3. Run drift, accessibility, localization, build, and visual checks; attach evidence.
4. Roll back by reverting the consumer imports and generator changes together with the token-source change. No data or deployment migration is required.
